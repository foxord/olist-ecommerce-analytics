# Как устроена база

Девять таблиц находятся в схеме `olist`. В таблицах хранятся исходные наблюдения. Для аналитики поверх них построены представления. [Схема и индексы](../sql/01_schema.sql) · [Загрузчик](../sql/02_load.py)

## Ключи и связи

| Таблица | Первичный ключ | Что показывает проверка исходных строк |
|---|---|---|
| orders | order_id | 99 441 отдельный заказ. Ссылка на customers по customer_id. |
| customers | customer_id | 99 441 запись клиента при оформлении, но 96 096 разных customer_unique_id за все статусы. Второй идентификатор нужен для истории покупателя. |
| order_items | (order_id, order_item_id) | Номер позиции начинается заново в каждом заказе. Пара уникальна. Есть внешние ключи к orders, products и sellers. |
| order_payments | (order_id, payment_sequential) | В заказе может быть несколько частей оплаты, каждая имеет свой порядковый номер. Пара уникальна. |
| order_reviews | review_row_id | И order_id, и review_id повторяются. Пара (order_id, review_id) уникальна в этой версии данных. Технический ключ позволяет загрузить строки без предположений о следующих выгрузках. Внешний ключ к orders. |
| products | product_id | Для 13 товаров название категории есть только на португальском. Внешний ключ к неполному переводу исключил бы эти строки. Связь со словарём используется через LEFT JOIN. |
| sellers | seller_id | Один продавец может продать много позиций. Штат продавца и штат доставки обозначают разные места. |
| category_translation | product_category_name | У каждой из 71 переведённой категории одно название на английском. |
| geolocation | geo_row_id | 19 015 префиксов на 1 000 163 строки. Используется технический ключ и сохраняются повторы. Префикс не подходит для внешнего ключа или прямого JOIN к заказам. |

Почтовые префиксы хранятся в TEXT для сохранения начальных нулей. Для цен и платежей выбран NUMERIC(12,2). Даты имеют тип TIMESTAMP, поскольку в CSV моменты записаны без часового пояса. Опечатки `lenght` в именах двух колонок совпадают с исходными заголовками. Отсутствующие комментарии и даты хранятся как NULL.

## Загрузка и повторный запуск

В базе проекта скрипт сначала создаёт таблицы, затем полностью обновляет **эти девять таблиц**. Он загружает справочники до заказов, а позиции, оплаты и отзывы после заказов. COPY читает CSV с кавычками, в том числе отзывы с переводами строк. Перед завершением транзакции для каждой таблицы сравниваются число записей CSV и COUNT(*) из PostgreSQL. Технические номера при повторной загрузке начинаются с единицы и следуют порядку строк в файле. При ошибке PostgreSQL откатывает обновление целиком. Результат загрузки должен совпасть с этой таблицей.

| Таблица | Строк в CSV | Ожидается в PostgreSQL |

| customers | 99 441 | 99 441 |
| orders | 99 441 | 99 441 |
| order_items | 112 650 | 112 650 |
| order_payments | 103 886 | 103 886 |

| sellers | 3 095 | 3 095 |

## Зачем индексы

Первичные ключи PostgreSQL уже индексирует. Например, индекс пары (order_id, order_item_id) умеет искать позиции по первому столбцу. Для отзывов нужен отдельный индекс по order_id. Индексы по product_id и seller_id помогают при выборке позиций одного товара или продавца. Индексы по customers.customer_unique_id и orders.customer_id поддерживают поиск истории клиента. Индекс по времени покупки помогает выбрать узкий период. Если запрос читает почти всю таблицу, планировщик может предпочесть последовательное чтение.

[Эксперимент EXPLAIN ANALYZE](../sql/02_index_plan.sql) выбирает заказы за 15 января 2018 года. На временной копии выполняется один и тот же запрос до и после создания индекса. В выводе можно сравнить тип сканирования, число прочитанных страниц и Execution Time. Время зависит от компьютера и кеша.
